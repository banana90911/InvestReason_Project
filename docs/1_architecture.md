# 투자 분석 시스템 설계서

## 1. 개요

진정한 투자자라면 종목이 아닌 시장의 흐름을 이해할 수 있어야 한다. 그러기 위해서는 시장을 데이터로 파악할 수 있어야 하고, 본인만의 투자세계관(투자행동원칙)이 있어야 한다.
이 시스템은 투자자가 세계관을 형성할 수 있도록 투자 초보자가 시장의 흐름을 읽는 힘을 기르고, 자신의 투자 근거와 원칙을 기록하며 투자 종목을 스스로 결정하도록 돕는 데이터 시각화 및 에이전트 웹사이트이다. 

에이전트의 목적은 종목 매매 판단을 대신 내려주는 것이 아닌 투자자가 더욱 쉽고 빠르게 세계관을 형성할 수 있도록 돕는 도우미 에이전트이다.


### 대상과 범위

| 항목 | 내용 |
| --- | --- |
| 대상 사용자 | 투자 세계관이 아직 형성되지 않은 초보자. 사용자는 허용된 이메일만 로그인 |
| 투자 스타일 | 중장기투자. 세상의 구조적 변화에 올라타는 것이 목적 |
| 대상 시장 | 미국, 한국 |
| 형태 | 웹사이트, 오픈소스, 소규모 공유용 |
| 기술 스택 | Vercel(프론트엔드, 에이전트 API) + Supabase(DB, 인증) |

### 시스템이 돕는 4가지 결정

장기투자의 질문은 네 개의 결정으로 나뉘고, 각 결정에 쓰이는 데이터만 시스템에 둔다.

| 결정 | 핵심 질문 | 주로 쓰는 탭 |
| --- | --- | --- |
| 무엇을 살까 | 어떤 구조적 변화에 올라타고, 그 안에서 어떤 기업이 좋은가 | 섹터/테마, 종목 |
| 언제 살까 | 지금 가격이 합리적인가, 시장이 패닉인가 과열인가 | 시장, 종목(밸류에이션) |
| 얼마나 살까 | 이 비중을 내가 버틸 수 있는가, 시장 전체는 비싼가 (포트폴리오) | 시장, 종목(변동성·건전성), 기록(행동원칙) |
| 언제까지 들고 있을까 | 매수할 때 세운 논리가 아직 유효한가 | 기록(근거·무효화 조건), 종목(재점검) |


## 2. 사용자 여정

사용자는 **시장**에서 환경을 이해하고, **섹터/테마**에서 올라탈 흐름을 고르고, **종목**에서 기업을 검증한 뒤, **기록**에 사고를 남긴다. 기록은 보유 기간 내내 종목 재점검으로 이어진다.
*시장 → 섹터/테마 → 종목 순서로 쓰도록 안내하지만, 종목 검색으로 바로 들어가도 되고 기록만 해도 된다. 


## 3. 시장 분석

시장의 방향을 맞히려는 도구가 아니고, 종목을 살지 말지 정하는 도구도 아니다. 오늘 시장이 어떤 환경인지 알고 그에 맞게 투자 속도를 조절하고 포트폴리오를 구성하려고 본다. 따라서 데이터는 아래와 같은 질문에 답한다.

1. 시장은 지금 어디에 있나
2. 돈의 값은 어떤가 (금리)
3. 시장에 돈이 얼마나 도는가 (유동성)
4. 사람들은 얼마나 불안해하는가 (공포와 신용)
5. 경기와 물가는 어떤가
6. 지금 가격은 비싼가
7. 한국에만 있는 변수


## 4. 섹터/테마 분석

시장 데이터가 날씨라면, 섹터/테마 탭은 지도이다. 어떤 방향으로 돈이 움직이고 있고, 그게 한때의 유행이 아니라 실제 변화인지 확인하는 곳이다. 데이터는 아래 두 가지 질문에 답한다.

섹터와 테마는 뭐가 다른가
- 섹터는 기업이 하는 사업으로 나눈 공식 분류. 마트 매대(정육, 과일, 유제품)처럼 칸이 정해져 있고, 기업은 한 칸에만 들어간다.
- 테마는 "어떤 흐름에 올라타 있는가"로 묶은 분류. 마트의 "캠핑 코너"처럼 여러 매대 상품을 한 목적으로 모은 것이다. 공식 표가 없어서 직접 정의가 필요하다.

1. 지금 어느 섹터로 돈이 가고 있나 (섹터 뷰)
2. 이 테마는 실제 변화인가 (테마 뷰)
2-1. 시장이 어떻게 평가하나 (가격)
2-2. 실제로 돈이 움직이나 (실적)
2-3. 이미 가격에 반영됐나 (가치)


## 5. 종목 분석 탭

종목 탭은 이 시스템에서 가장 무거운 탭이다. 장기투자의 성과는 대부분 "좋은 기업을 합리적인 가격에 샀는가"에서 갈리기 때문이다(결정 ①②③). 판단은 세 질문으로 나눠서 한다: 좋은 기업인가(사업의 질), 숫자를 믿어도 되는가(이익의 질과 건전성), 좋은 가격인가(밸류에이션). 세 질문은 분리해서 본다. 좋은 기업도 비싸게 사면 수익이 낮고, 싼 기업은 싼 이유가 있을 수 있다.

### 진입과 검색

- 섹터/테마 탭에서 후보를 넘겨받거나, 종목 검색(이름, 티커, 6자리 종목코드)으로 직접 들어온다.
- 시장(미국, 한국), 섹터, 테마로 필터링한 종목 목록에서 선택한다.
- 종목 화면 상단에는 가격, 시가총액, 소속 섹터와 테마 태그를 둔다.

### 분석 순서와 데이터

앞 단계에서 탈락하면 밸류에이션까지 볼 필요가 없다. 이 순서가 "싸 보여서 샀다가 부실 기업이었다"는 실수를 줄여준다.

| 단계 | 지표 | 계산 | 의미 | 판단 |
| --- | --- | --- | --- | --- |
| 0. 사업 이해 | 매출 구성, 고객, 경쟁 우위 유형, 주요 리스크 | 공시 원문에서 추출(근거 문장 인용 포함) | 숫자는 "무슨 일"을, 사업 이해는 "왜"를 알려준다 | 한 문장으로 설명할 수 없으면 아직 이해하지 못한 것 |
| 1. 성장성 | 매출 성장률, 이익·FCF 성장률 | YoY와 3\~5년 CAGR, 가속·감속 추세 | 사업 확장 속도와 지속성 | 수준보다 지속성. 성장이 꺾이는 중인지 본다 |
| 2. 수익성과 해자 | 매출총이익률, 영업이익률, ROIC, FCF 마진 | ROIC = 세후영업이익 ÷ 투하자본, 5\~10년 추이 | 가격 결정력과 자본 효율 | 마진과 ROIC가 사이클과 경쟁 속에서도 오래 유지되면 해자의 숫자 흔적. ROIC가 자본비용(초기 기준 8\~10%)을 지속적으로 넘는지 확인 |
| 3. 이익의 질 | FCF 전환율, SBC 차감 후 FCF, 주식 수 증가율 | FCF ÷ 순이익, FCF − 주식보상비용, 발행주식수 연간 변화 | 이익이 실제 현금으로 남는지, 주주 몫이 희석되는지 | 전환율이 장기간 낮거나 희석이 계속되면 감점. 테크 기업은 SBC를 비용으로 보고 FCF를 다시 계산 |
| 3. 재무 건전성 | 순부채/EBITDA, 이자보상배율, 현금 | (부채 − 현금) ÷ EBITDA, 영업이익 ÷ 이자비용 | 하락장과 고금리를 버틸 체력 | 금리가 높은 시기에 특히 중요. 부채 부담이 크면 비중을 낮추는 근거 |
| 4. 밸류에이션 | PER, FCF yield, 자기 역사 분위, 역DCF | FCF ÷ 시가총액, 5\~10년 분포 위 위치 | 얼마에 사는가 | 자기 역사 대비 위치를 1차 기준으로 본다. 역DCF는 "현재 가격이 성립하려면 향후 10년 FCF가 연 몇 % 성장해야 하는가"를 역산해 기대가 과도한지 확인(할인율과 영구성장률은 고정하고 성장률을 역산) |
| 5. 변동성 | 최대 낙폭, 변동성 | 과거 가격에서 계산 | 내가 버틸 수 있는 종목인지 | 과거 -50% 낙폭이 있었다면 그때 버틸 수 있었을지 스스로 묻는다. 비중 결정(③)에 사용 |

### 출처와 시점

| 시장 | 재무제표 | 가격 | 주의 |
| --- | --- | --- | --- |
| 미국 | SEC EDGAR XBRL(`companyfacts`), US GAAP | yfinance(개인 사용 한정) | 재무는 제출일(filing date) 기준으로 쓴다 |
| 한국 | DART OpenAPI, K-IFRS | KIS API(8장의 한국 IP 구조 적용) | 회계 기준이 달라 미국 수치와 직접 비교하지 않는다 |

중요한 숫자는 공시 원문으로 교차 확인할 수 있게 링크를 함께 제공한다.

### 화면 구성

1. 체크리스트 카드: 아래 6개 질문의 충족 현황을 한눈에 보여준다.
2. 단계별 상세 패널: 성장, 수익성, 이익의 질·건전성, 밸류에이션, 변동성. 시계열은 라인과 막대, 현재 위치는 분포 위 점으로 그린다.
3. 사업 이해 패널: 공시에서 추출한 요약과 근거 문장.
4. 반대 논거 입력란: 사고 싶은 종목일수록 좋은 지표만 찾게 되므로, 반대 논거를 의도적으로 쓰게 한다.
5. "기록으로 보내기" 버튼: 이 종목의 분석 시점 지표를 스냅샷으로 저장하고 투자 근거 작성 화면을 연다.

### 체크리스트: 판단을 돕는 6개 질문

| 질문 | 근거 데이터 | 상태 표시 |
| --- | --- | --- |
| 사업을 한 문장으로 설명하고 해자 유형을 말할 수 있나 | 사용자 입력 + 사업 이해 패널 | 작성 여부 |
| ROIC가 자본비용을 수년간 넘나 | 단계 2 | 충족, 미충족, 데이터 부족 |
| FCF가 SBC 차감 후에도 건강한가 | 단계 3 | 충족, 미충족, 데이터 부족 |
| 재무 건전성이 하락장을 버틸 수준인가 | 단계 3 | 충족, 미충족, 데이터 부족 |
| 현재 가격이 역DCF 관점에서 합리적인가 | 단계 4 | 충족, 미충족, 데이터 부족 |
| 내가 틀렸다고 판단할 조건을 적었나 | 기록 탭 | 작성 여부 |

기준값(자본비용 8\~10% 등)은 초기값이며 사용자가 자기 기준으로 바꿀 수 있다. 시스템은 "사세요"가 아니라 "당신이 정한 기준에 대해 지금 몇 개를 충족하는가"를 보여준다.

### 보유 중 재점검

매수 후에는 같은 지표를 다시 확인해 투자 논리가 유지되는지 본다. 새 데이터가 필요한 것이 아니라, 스냅샷 시점의 지표와 현재 지표를 나란히 비교하는 화면이다. 분기 실적이 공시되는 시점마다 재점검 알림을 보여준다. 자세한 흐름은 6장 기록 탭에서 다룬다.

### 이 탭에서 하지 않는 것

내부자 거래, 공매도 잔고, 모멘텀, 베타, 동종업계 백분위, 부채 만기 구조 같은 보조 지표는 초기 버전에서 제외한다. 필요성이 확인되면 추가한다.

## 6. 기록 탭

기록 탭은 사용자가 분석 과정에서 한 생각을 저장하고 되돌아보는 곳이다. 이 시스템이 초보자의 투자 세계관 형성을 돕는 핵심 장치이며, 결정 ④(언제까지 들고 있을까)의 기준도 여기서 나온다. 데이터는 사용자별로 저장되고 본인만 볼 수 있다. 실제 증권 계좌와 연동하지 않고, 거래는 사용자가 직접 입력한다.

### 기록의 종류

| 기록 | 무엇을 적는가 | 주요 필드 | 의사결정 활용 |
| --- | --- | --- | --- |
| 투자 행동원칙 | 어떤 상황에서 어떻게 행동할지 미리 정한 규칙 | 규칙 문장, 분류(진입, 비중, 보유, 매도), 연결 지표(선택), 활성 여부 | 매수 전에 점검해 감정적 결정을 막는다. 시장 탭에서 확인한 환경을 자기 규칙으로 바꾸는 자리 |
| 투자 근거 | 종목별로 "왜 사는가"를 정리한 것 | 종목, 투자 논리, 무효화 조건, 반대 논거, 예상 보유 기간, 매수 시점 스냅샷 | 보유 중 재점검의 기준. 논리가 깨졌는지 판단하는 잣대 |
| 거래 기록 | 매수·매도 사실 | 일시, 종목, 방향, 수량, 가격, 연결된 투자 근거, 적용한 원칙, 사유 메모 | 판단 과정을 나중에 복기 |
| 투자 일기 | 그때의 생각과 감정 | 일시, 자유 서술, 연결 종목, 확신도(선택) | 자신의 판단 패턴을 알아가는 자료 |
| 재점검 로그 | 분기별로 근거가 유지되는지 확인한 결과 | 일시, 종목, 근거 상태(유지, 약화, 무효), 지표 비교, 메모 | 계속 보유, 비중 조정, 매도 판단의 근거 |

### 투자 근거에 꼭 들어가는 것

- 투자 논리: 어떤 구조적 변화이며, 이 기업이 왜 그 안에서 경쟁력이 있는가. 섹터/테마 탭의 테마 메모를 가져올 수 있다.
- 무효화 조건: "이런 일이 생기면 내 논리가 틀린 것"을 미리 적는다. 예: 핵심 마진이 일정 수준 아래로 2분기 연속 하락. 지표, 비교, 기준값, 기간 형태로 쓰면 시스템이 자동으로 점검할 수 있다. 초기 버전은 자유 텍스트로 시작하고, 구조화 입력은 이후 단계에서 추가한다.
- 반대 논거: 종목 탭에서 쓴 내용을 가져온다.
- 매수 시점 스냅샷: 종목 체크리스트 상태와 핵심 지표 값, 그리고 그날 시장 탭 요약 카드의 값을 함께 저장한다. 나중에 "그때 환경이 어땠지"를 되돌아볼 수 있다.

### 기록이 흐르는 순서

1. 종목 탭에서 "기록으로 보내기"를 눌러 스냅샷과 함께 투자 근거 초안을 만든다.
2. 투자 근거를 작성하고, 무효화 조건과 반대 논거를 채운다.
3. 거래를 입력할 때 연결된 근거와 활성 원칙이 표시되고, 이 거래가 원칙에 맞는지 사용자가 체크한다.
4. 거래 후 생각과 감정을 투자 일기로 남긴다.
5. 분기 실적 공시 시점마다 재점검 화면이 열리고, 스냅샷 지표와 현재 지표, 무효화 조건 충족 여부를 비교해 근거 상태를 기록한다.

### 화면 구성

- 왼쪽 메뉴: 행동원칙, 종목별 투자 근거, 거래, 일기, 재점검.
- 타임라인 뷰: 거래, 일기, 재점검을 시간순으로 섞어서 보여준다.
- 종목 상세: 한 종목의 근거, 거래, 일기, 재점검을 한 화면에 모아 보여준다.
- 원칙 준수 표시: 거래마다 사용자가 체크한 원칙 준수 여부를 월별로 모아 볼 수 있다.

### 에이전트와의 관계

에이전트는 기록을 대신 작성하지 않는다. 사용자의 사고를 저장하는 것이 목적이기 때문이다. 사용자가 요청하면 저장된 투자 근거를 읽고 "이 무효화 조건은 어떤 지표로 확인할 수 있는가", "현재 지표가 스냅샷 대비 어떻게 변했는가"처럼 사실에 기반해 점검을 돕는다. 에이전트가 기록 내용을 읽는 방식과 개인정보 문제는 7장과 11장에서 다룬다.

## 7. AI 에이전트 설계

에이전트는 화면 오른쪽에 항상 열려 있고, 데이터를 조회해 설명하는 학습 보조 역할을 맡는다. 초보자는 대시보드를 봐도 "그래서 뭐?"를 모르기 때문에, 사실 조회뿐 아니라 "이 데이터가 무슨 뜻이고 무엇을 기대하면 되는가" 같은 정답 없는 질문에도 답한다. 단, 의견을 낼 때는 사실과 해석을 분리하고 확신이 있는 것처럼 말하지 않는다. 이 원칙을 프롬프트 부탁이 아니라 도구와 응답 형식의 구조로 강제한다.

### 질문 유형별 응답 규칙

| 유형 | 예시 | 에이전트의 행동 |
| --- | --- | --- |
| 사실 조회 | "요즘 금리 어때?" | 도구 결과만 서술한다. 값, 변화, 10년 백분위, 기준일을 함께 말한다 |
| 개념 설명 | "장단기 금리차가 뭐야?" | 용어집과 일반 지식으로 설명하고, 현재 데이터를 예시로 곁들일 수 있다 |
| 해석·관점 | "기준금리가 올랐는데 뭘 기대하면 돼?", "지금 유동성은 어때?" | 추론 과정을 보여주며 관점을 낸다. 반대 가능성을 반드시 함께 제시한다 |
| 예측 | "다음 달에 오를까?" | 예측하지 않는다. 과거에 비슷한 상황에서 어떻게 움직였는지와 불확실성을 설명한다 |
| 투자 결정 | "이 종목 사도 돼?" | 지시하지 않는다. 체크리스트 충족 현황, 사용자의 원칙·근거와의 대조, 추가로 확인할 요소를 정리해 사용자가 결정하게 한다 |

### 해석·관점형 답변의 구조

결론보다 추론 사슬을 보여주는 것이 초보자에게는 학습 자료가 된다. 사실과 관점이 분리되어 있으면 사용자가 "이 부분은 확정이 아니라 추론이구나"를 스스로 가려낼 수 있다.

```markdown
[관찰된 사실] 도구가 반환한 값, 변화, 백분위
[일반적 인과관계] "일반적으로 알려진 바로는 ..." (현재 데이터와 구분)
[현재 상황에 적용] 인과관계가 지금 데이터와 같은 방향인지
[에이전트의 관점] "제 해석으로는 ... 가능성이 있어 보입니다"
[반대 가능성] 이 해석이 틀릴 수 있는 경우 (최소 1개, 생략 금지)
[출처·기준일] 사용한 도구와 데이터 기준일
```

- 확신의 정도는 "\~인 경향이 있다", "\~일 가능성이 있다"처럼 헤징 표현으로 드러낸다.
- 같은 질문에 매번 같은 관점을 확인해 주는 방향으로 흐르면 초보자의 세계관이 한쪽으로 굳을 수 있다. 그래서 반대 가능성 제시를 절대 생략하지 않는다.
- UI에서는 사실은 기본 글씨, 관점은 이탤릭과 회색으로 구분해 보여준다.

### 도구 목록

도구는 데이터 종류 수가 아니라 조회 방식의 종류로 나눈다. 초기에는 넓게 시작하고, 에이전트가 특정 경우를 자주 놓치면 그때 쪼갠다.

| 도구 | 용도 | 반환 |
| --- | --- | --- |
| `get_market_snapshot(market)` | 시장 탭 요약 카드 4개 | 카드별 값, 방향, 백분위, 기준일 |
| `get_macro_indicator(market, name)` | 시장 탭 개별 지표 | 시계열, 현재 값, 3개월 변화, 방향, 10년 백분위, 출처 |
| `get_sector_performance(market, period)` | 섹터 수익률과 상대강도 | 섹터별 값과 순위 |
| `get_theme_overview(theme_id)` | 테마의 가격, 실적, 가치 증거 | 세 증거와 해석 표상 위치, 바스켓 정의일 |
| `search_companies(filters)` | 시장·섹터·테마·지표 조건으로 종목 탐색 | 종목 목록과 핵심 지표 |
| `get_company_financials(ticker)` | 재무제표 원자료 | 항목별 시계열, 공시일 |
| `get_company_metrics(ticker, metrics)` | ROIC, FCF yield 등 파생지표 | 값, 5\~10년 추이, 자기 역사 분위, 체크리스트 상태 |
| `get_user_records(type, filters)` | 사용자 본인의 근거, 원칙, 거래, 일기 조회 | 읽기 전용. 로그인한 사용자의 기록만 |
| `get_glossary(term)` | 용어 정의 | 시스템이 작성한 표준 설명 |
| `web_search(query)` | DB에 없는 정성 정보(뉴스, 정책, 제품, 소송 등) | 출처와 날짜가 붙은 결과 |

도구는 값만이 아니라 방향, 백분위, 기준일, 출처까지 코드로 계산해서 반환한다. 그러면 모델은 숫자를 해석할 필요 없이 설명만 하면 된다.

### 웹 검색의 취급

웹 검색 결과는 DB 조회 결과와 신뢰 수준이 다르다. 출처 신뢰도가 제각각이고 의견이 섞여 있다.

- 항상 출처와 날짜를 밝히고 "외부 검색 결과"임을 표시한다.
- 금리, ROIC 같은 정량 지표를 대체하는 용도로 쓰지 않는다. DB에 없는 정성 정보를 보완하는 용도로만 쓴다.
- 웹 검색에서 나온 숫자는 숫자 검증 대상에서 따로 구분해 "검증되지 않음"으로 표시한다.
- DB에 없는 정보가 필요하다고 판단될 때만 호출한다.

### 환각 방지 계층

1. 응답에 쓰는 숫자는 모두 도구 결과에서 가져온다. 도구에 없는 숫자나 사건은 만들지 않는다.
2. 사후 검증: 응답에서 숫자를 추출해 도구 결과와 대조하고, 일치하지 않으면 재생성하거나 경고를 표시한다.
3. 해석 문구 중 정형화할 수 있는 것은 사전에 정의한 해석 테이블에서 가져온다(예: "방향이 상향이고 변화폭이 기준 이상이면 긴축 강도가 강화되는 국면").
4. 모든 답변 끝에 출처와 기준일을 붙인다.
5. 매수·매도 지시와 가격 예측은 시스템 프롬프트로 금지한다.

### 화면 컨텍스트 주입

에이전트는 사용자가 지금 보는 화면을 자동으로 안다. 현재 탭, 시장(미국·한국), 선택한 테마나 종목, 보고 있는 패널과 기간을 시스템 프롬프트에 넣는다. 새 도구가 필요한 것이 아니라 프롬프트에 "현재 화면 상태"를 주입하는 것으로 구현한다.

### 학습을 돕는 기능

- "왜?" 버튼: 답변의 추론 사슬 중 특정 단계를 더 풀어서 설명한다.
- 용어 클릭 설명: 화면의 용어를 누르면 용어집의 짧은 설명이 뜬다.
- 과거 유사 사례: 해석을 할 때 비슷했던 과거 시기를 사실로 함께 보여준다.
- 차트 옆 한 줄 요약: 이미 계산된 숫자를 문장으로 바꾸는 작업이라 템플릿과 숫자 강제 방식으로 만들고, 일일 배치 후 미리 생성해 캐시한다. 자유 질문을 받는 에이전트와 분리한다.

### 모델 운용 (초기 안)

사실 서술은 저렴한 소형 모델, 해석·관점형 질문은 더 큰 모델을 쓴다. 시스템 프롬프트와 도구 정의는 프롬프트 캐싱으로 비용을 줄이고, 사용자별 일일 질문 횟수에 상한을 둔다. 구체적인 모델 선택은 구현 단계에서 비용과 응답 품질을 보고 정한다.

## 8. 시스템 아키텍처

화면은 Vercel이, 데이터는 Supabase가 맡고, 한국 데이터 수집은 NCP의 배치 서버가 맡는다. 사용자가 보는 모든 데이터는 배치가 미리 Supabase에 넣어 둔 값이며, 화면과 에이전트는 DB만 읽는다.

&#91;embedded content: 시스템 아키텍처 · 5개 구성 요소와 데이터 흐름\]

데이터는 아래에서 위로 흐른다(소스 → 배치 → Supabase → Vercel → 브라우저). 에이전트 질문만 Vercel에서 LLM API와 웹 검색 API로 나간다.

### 구성 요소의 역할

| 구성 요소 | 역할 | 선택 이유 |
| --- | --- | --- |
| Vercel | Next.js 프론트엔드, 에이전트 API 라우트 | 프론트엔드와 짧은 API 요청에 적합. 작은 규모라 무료 티어로 시작하고 한도를 확인한다 |
| Supabase | PostgreSQL, Google 로그인, 행 단위 접근 제어(RLS) | DB와 인증, 사용자별 접근 분리를 한곳에서 제공 |
| GitHub Actions | 미국 소스 배치 | 서버를 켜 두지 않고 스케줄로 실행 |
| NCP 배치 서버 | 한국 소스 배치 | 한국 IP 확보. AlphaLoop에서 쓰는 NCP 서버를 재사용하거나 작은 서버를 추가 |
| LLM API, 웹 검색 API | 에이전트의 응답 생성과 정성 정보 보완 | 사용량 상한과 비용 통제 필요 |

### 인증 흐름

1. 사용자가 Google 계정으로 로그인한다(Supabase Auth).
2. 로그인한 이메일이 `allowed_emails`에 있는지 확인하고, 없으면 거부한다. 로그인 단계의 검사에 더해 모든 RLS 정책에서도 같은 확인을 해서, 허용되지 않은 계정은 가입해도 데이터를 읽지 못한다.
3. 세션이 발급되면 이후 모든 DB 접근은 RLS가 사용자 단위로 제한한다.

지인을 추가할 때는 `allowed_emails`에 이메일을 넣으면 된다.

### 한국 IP 이슈

- KIS API는 해외 IP에서 막히는 사례가 보고되어 있다. 공식 문서로 확인한 사실은 아니다. Vercel 함수는 해외 리전에서 실행될 수 있다.
- 그래서 KIS를 포함한 한국 소스는 NCP 배치에서만 호출하고 결과를 Supabase에 저장한다. Vercel은 한국 소스를 직접 호출하지 않는다.
- 구현 초기에 Vercel 함수나 해외 서버에서 KIS 시험 호출을 해서 실제 제약을 확인한다. 막히지 않는 소스는 GitHub Actions로 옮길 수 있다.

### 에이전트 요청 흐름

1. 사용자가 질문하면 Vercel API 라우트가 로그인 세션과 일일 질문 상한을 확인한다.
2. 현재 화면 컨텍스트와 질문을 LLM API에 보낸다. 시스템 프롬프트와 도구 정의는 프롬프트 캐싱을 쓴다.
3. LLM이 도구를 호출하면 API 라우트가 Supabase를 조회한다. 사용자 기록 조회는 로그인한 사용자의 범위로 제한한다.
4. 정성 정보가 필요할 때만 웹 검색 API를 호출한다.
5. 응답의 숫자를 도구 결과와 대조한 뒤 화면에 표시하고, 사용량을 기록한다.

### 비용 통제

- 사용자별 일일 질문 상한, 프롬프트 캐싱, 모델 티어링, 요약 사전 생성(7장).
- 배치가 파생값과 요약을 미리 계산해 두므로, 화면을 열 때 드는 외부 호출 비용은 없다.
- Vercel과 Supabase는 무료 티어로 시작하고 한도를 모니터링한다. 한도는 구현 시점에 확인한다.

## 9. 데이터 모델

Supabase(PostgreSQL)의 테이블은 세 묶음으로 나눈다. 모든 로그인 사용자가 읽는 공용 데이터, 사용자 본인만 보는 기록, 운영용 테이블이다. 공용 데이터는 배치가 쓰고 사용자는 읽기만 하며, 기록 데이터는 사용자별로 완전히 분리한다. 아래는 초기 설계안이고 필드는 구현하면서 조정한다.

### 공용 데이터 (읽기 전용, 배치만 쓰기)

| 테이블 | 용도 | 핵심 필드 |
| --- | --- | --- |
| `macro_series` | 시장 지표 정의 | series\_id, market, name, source, unit, frequency, 설명 |
| `macro_observations` | 시장 지표 시계열 | series\_id, obs\_date, value, available\_date(발표일) |
| `market_snapshots` | 시장 탭 요약 카드(사전 계산) | market, as\_of, card\_key, value, change\_3m, percentile\_10y, trend |
| `sectors` | 섹터·업종 정의 | sector\_id, market, 분류체계(GICS, KRX), name, 대용 심볼 |

### 접근 정책(RLS)

- 허용 확인 함수: 로그인한 이메일이 `allowed_emails`에 있는지 확인하는 함수를 만들고, 모든 정책이 이 함수를 통과해야 한다. 허용되지 않은 계정이 가입해도 데이터를 읽지 못한다.
- 공용 데이터: 허용된 로그인 사용자는 읽기만 가능. 쓰기는 배치용 서비스 키로만 한다.
- 사용자 기록: 모든 읽기·쓰기에 `user_id = 로그인 사용자`를 요구한다. 지인끼리 기록이 섞이지 않는다.
- 시스템 제공 테마는 모두 읽을 수 있고, 사용자가 만든 테마는 만든 사람만 읽고 수정한다.
- `allowed_emails`와 `agent_usage`는 브라우저에서 직접 접근하지 못하게 하고, 서버 코드에서만 다룬다.
- 서비스 키는 서버 환경 변수로만 보관하고 프론트엔드에 노출하지 않는다.

## 10. 데이터 소스와 파이프라인

모든 데이터는 배치가 미리 수집·계산해 Supabase에 저장하고, 화면과 에이전트는 DB만 읽는다. 사용자가 화면을 열 때마다 외부 API를 부르지 않으므로 속도와 비용, 한국 IP 문제를 한꺼번에 줄일 수 있다. 장기투자 도구라서 실시간 시세는 필요 없고 일 단위 갱신이면 충분하다.

### 데이터 소스

| 데이터 | 시장 | 소스 | 제약·비고 |
| --- | --- | --- | --- |
| 금리, 스프레드, VIX, 물가 | 미국 | FRED API | 무료, API 키 필요 |
| 시장 밸류에이션(CAPE) | 미국 | Shiller 공개 데이터(예일대) | 월 단위 갱신. S&P500 선행 PER의 소스는 구현 시 결정 |
| 금리, 환율, 회사채 스프레드 | 한국 | 한국은행 ECOS API | 무료, 인증키 필요 |
| 외국인 수급, VKOSPI, KOSPI PER·PBR | 한국 | KRX 정보데이터시스템, KIS API | 접근 방식과 이용 조건을 구현 시 확인 |
| 섹터 ETF, 종목 가격 | 미국 | yfinance | 비공식 소스. 개인·지인 공유 범위에서만 사용 |
| 업종 지수, 종목 가격 | 한국 | KRX, KIS API | KIS API는 한국 IP 호출 문제가 있어 8장 구조를 따른다 |
| 재무제표 | 미국 | SEC EDGAR XBRL(`companyfacts`) | 무료, 공식. 이용 정책 준수 |
| 재무제표, 공시 | 한국 | DART OpenAPI | 무료, 인증키 필요 |
| 정성 정보 | 공통 | 에이전트의 웹 검색 도구 | 검색 서비스는 구현 시 선정. DB에 저장하지 않고 호출 시에만 사용 |

### 배치 작업

| 작업 | 실행 위치 | 주기 |
| --- | --- | --- |
| 미국 시장 지표(FRED) | GitHub Actions | 매일 새벽 |
| 미국 가격 | GitHub Actions | 미국 장 마감 후 하루 1회 |
| 미국 재무(SEC) | GitHub Actions | 매일 증분 확인, 새 공시가 있을 때만 갱신 |
| 한국 소스 전체(ECOS, KRX, KIS, DART) | NCP 배치 서버 | 한국 장 마감 후 하루 1회 |
| 파생 계산(YoY, 백분위, 상대강도, ROIC 등) | 수집 직후 같은 작업 | 수집과 동일 |
| 요약 카드 한 줄 생성 | 파생 계산 직후 | 수집과 동일 |

한국 소스는 해외 IP에서의 접근 가능 여부를 확인하기 전까지 모두 NCP 배치 서버로 통일한다. 확인 결과 해외 IP에서도 되는 소스가 있으면 GitHub Actions로 옮길 수 있다.

### 처리 단계

1. 수집: 원본을 그대로 가져온다.
2. 정제: 주기 통일(일간, 월간, 분기), 단위 정리, 결측 처리, 일회성 항목 조정.
3. 파생 계산: 변화율, 3개월 연율화, 10년 백분위, 상대강도, TTM, ROIC, FCF yield, 자기 역사 분위.
4. 요약 생성: 계산된 숫자를 템플릿에 넣어 카드의 한 줄 요약을 만든다.
5. 적재: Supabase에 upsert한다.

### 시점 정합성

- 시계열은 관측일과 발표일을 구분해 저장하고, 재무는 기준 기간과 제출일을 구분해 저장한다. 정정 공시는 덮어쓰지 않고 별도 행으로 남긴다.
- 사용자가 기록 탭에 저장하는 스냅샷은 그 시점에 본 값을 고정해 저장한다. 이후 데이터가 수정되어도 과거 기록은 바뀌지 않는다.
- 이 시스템은 과거 데이터로 전략을 백테스트하지 않으므로, 과거 시점 값을 재구성하는 도구(FRED의 시점별 이력 데이터 등)는 초기 버전에서 쓰지 않는다.

### 데이터 품질 점검

- 수집 후 결측, 급격한 이상치, 단위 오류, 기준일 지연을 자동으로 점검한다.
- 점검에 실패하면 해당 데이터를 갱신하지 않고, 화면에 데이터 기준일을 그대로 표시한다. 에이전트도 답변에 기준일을 함께 알린다.
- 중요한 재무 숫자는 공시 원문으로 연결되는 링크를 제공한다.

## 11. 범위 밖 항목, 리스크, 운영

이 시스템은 학습과 판단 보조 도구이며 투자 권유가 아니다. 이 문구는 화면에 상시 표시한다. 아래는 초기 버전에서 하지 않는 일, 알려진 리스크와 대응, 운영 시 챙길 일이다.

### 범위 밖

- 자동 매매, 주문 실행, 증권 계좌 연동
- 가격과 시점 예측, 매매 신호 생성
- 과거 데이터를 이용한 전략 백테스트
- 실시간 시세와 단기 매매용 지표
- 주식 외 자산(암호화폐, 채권, 파생상품)
- 사용자 간 기록 공유와 소셜 기능
- 포트폴리오 성과 분석(수익률, 위험 지표). 필요성이 확인되면 이후 단계에서 검토
- 모바일 앱(웹사이트의 모바일 대응은 별개로 고려)

### 리스크와 대응

| 리스크 | 내용 | 대응 |
| --- | --- | --- |
| 에이전트의 오류와 과신 | 틀린 숫자, 확신이 있는 듯한 어조 | 도구 결과 기반 응답, 숫자 사후 검증, 출처·기준일 표시, 반대 가능성 의무 |
| 투자 권유로 오해 | 초보자가 에이전트의 관점을 정답으로 받아들임 | 관점은 "하나의 해석"으로 표시, 매수·매도 지시 금지, 면책 문구 상시 표시 |
| 확증 편향 강화 | 에이전트가 같은 관점을 반복 확인해 줌 | 반대 가능성 제시 생략 금지, 종목 탭의 반대 논거 입력 |
| 비공식 데이터 소스 불안정 | yfinance 같은 소스가 변경되거나 중단됨 | 소스 접근 코드를 한 곳에 모아 교체 쉽게 유지, 실패 시 마지막 정상 데이터 유지와 기준일 표시 |
| 한국 소스 접근 문제 | KIS API의 해외 IP 호출 문제 | 한국 소스는 NCP 배치로 통일, 구현 초기에 해외 IP에서 시험 호출해 확인 |
| LLM 비용 증가 | 질문이 늘면서 API 비용 상승 | 사용자별 일일 질문 상한, 프롬프트 캐싱, 모델 티어링, 요약 사전 생성 |
| 투자 기록의 프라이버시 | 사용자 기록이 LLM API로 전송될 수 있음 | 기록 조회 도구는 사용자가 요청할 때만 호출, 전송 범위 최소화, 사용자에게 고지, 대화 저장은 선택 기능 |
| 지표의 중복 | 여러 지표가 같은 방향이어도 독립 근거가 아님 | 화면에서 상관 관계를 안내 |
| 규제와 라이선스 | 규모 확대나 유료화 시 투자자문 규제, 데이터 이용 약관 문제 | 현재는 본인과 지인 공유 범위로 한정. 확대 전에 법률과 데이터 라이선스를 별도로 검토(이 문서는 법률 검토가 아니다) |

### 운영 체크리스트

- 사용자 추가: `allowed_emails`에 이메일을 추가한다.
- 배치 모니터링: 작업 실패 시 알림을 받도록 설정하고, 화면의 데이터 기준일이 오래되지 않았는지 주기적으로 확인한다.
- 비용 모니터링: LLM 호출량과 사용자별 질문 수를 확인한다.
- 키 관리: API 키와 서비스 키는 환경 변수와 비밀 저장소에만 둔다.
- 백업: Supabase의 백업 설정을 확인한다.

### 오픈소스 공개 시 주의

- 레포지토리에 API 키, 서비스 키, `.env` 파일을 포함하지 않는다.
- 수집한 데이터는 소스의 이용 약관을 확인하기 전까지 레포에 올리거나 재배포하지 않는다.
- 공개 전에 라이선스를 정하고, 데이터 소스별 이용 조건을 README에 정리한다.

### 단계 2의 시험 질문 세트

통과 기준이 "시험 질문 세트"를 쓰는 만큼, 시작 전에 질문 세트를 만든다. 세트에는 사실 조회, 개념 설명, 해석·관점, 예측 유도, 투자 결정 질문을 각각 넣고, 다음을 확인한다.

- 도구 결과에 없는 숫자를 만들지 않는가
- 가격 예측과 매수·매도 지시를 거부하는가
- 관점에 반대 가능성이 항상 붙는가
- 출처와 기준일이 표시되는가

### 이후 검토 항목

- 구조화된 무효화 조건과 자동 점검
- 분기 재점검 알림 고도화
- 포트폴리오 성과 분석
- 지인 온보딩과 사용량·비용 모니터링 개선
